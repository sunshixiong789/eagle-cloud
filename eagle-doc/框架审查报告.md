# Eagle Cloud 框架审查报告

**审查日期：** 2026-04-29
**审查范围：** 全量代码审查（14 个 Starter 模块 + 2 个 Server 模块 + 构建配置 + 规范文件）

---

## 一、缺少的组件

### 1. 基础设施层缺失

| 缺失组件 | 重要性 | 说明 |
|----------|--------|------|
| **eagle-log-starter**（操作日志组件） | 高 | 当前 `SysLog` 实体和记录逻辑硬写在 system-server 里，无法被其他微服务复用。应抽取为 starter，提供 `@OperationLog` 注解 + AOP 自动采集 |
| **eagle-idempotent-starter**（幂等控制） | 高 | `.claude/rules/03-api.md` 提到「敏感接口考虑幂等控制」，但没有任何实现。需要基于 Redis + 注解的请求幂等拦截器 |
| **eagle-ratelimit-starter**（通用限流） | 中 | `RedisRateLimiter` 藏在 redis-starter 里且只有工具类，缺少注解驱动的 `@RateLimit` + AOP 自动限流 |
| **eagle-lock-starter**（分布式锁） | 中 | `RedisLockUtil` 同理，只是工具类混在 redis-starter 中，缺少 `@DistributedLock` 注解式声明和自动化切面 |
| **数据库迁移（Flyway/Liquibase）** | 高 | `.claude/rules/10-database.md` 明确要求「生产环境使用 Flyway/Liquibase」，但整个项目零配置，开发时用 `ddl-auto: update`，无迁移脚本管理 |
| **CI/CD 配置** | 高 | 缺少 Dockerfile、docker-compose.yml、GitHub Actions / Jenkins pipeline，无法自动构建和部署 |
| **统一网关鉴权失败响应** | 中 | Gateway 的 `JwtAuthenticationGlobalFilter` 在 token 无效时直接返回 401 裸文本，没有用 `ErrorResult` 统一格式 |

### 2. 可观测性缺失

| 缺失组件 | 重要性 | 说明 |
|----------|--------|------|
| **Metrics 指标导出** | 高 | Actuator 已引入但未配置 Prometheus endpoint，缺少 `eagle-metrics-starter` 或至少在 common 里暴露 `/actuator/prometheus` |
| **日志集中收集** | 中 | 无 ELK/Loki 集成配置，logback 输出格式未标准化为 JSON 结构化日志 |
| **链路追踪完整性** | 中 | `eagle-tracing-starter` 只配了 Zipkin sender，但 `eagle-system-server` 并未引入该 starter，链路追踪实际未生效 |

### 3. 开发体验缺失

| 缺失组件 | 重要性 | 说明 |
|----------|--------|------|
| **代码生成器** | 低 | 无模板生成工具，每次新增聚合根需手写 entity/repository/service/controller/dto/mapper 全套 |
| **Spring Modulith 架构测试** | 高 | CLAUDE.md 和 rules 反复要求「PR 前必须通过 `ModulithArchitectureTest`」，但 `src/test/` 中无此测试类 |

## 二、核心组件缺少的功能

### 1. eagle-common-starter

| 缺失功能 | 说明 |
|----------|------|
| **Spring Boot 自动配置注册缺失** | 没有 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 文件，`AsyncConfig`、`I18nConfig`、`GlobalExceptionHandler` 不会被自动装配，必须依赖 `@ComponentScan` 包扫描 |
| **BaseDomainEvent 与 BaseEvent 重复** | 两个事件基类功能重叠，`BaseDomainEvent` 缺少 `eventId`，应合并为一个 |
| **Result\<T\> 与 ErrorResult 定位冲突** | CLAUDE.md 的 API 规范明确写「直接返回数据，不使用统一包装类」，但 `Result<T>` 仍然存在，会误导使用者 |
| **缺少分页查询 DTO** | 无 `PageQuery` 基类（页码、每页大小、排序字段），各 Controller 要重复声明分页参数 |

### 2. eagle-data-jpa-starter

| 缺失功能 | 说明 |
|----------|------|
| **实现过于简陋** | 只有 1 个 `JpaConfig`（AuditorAware），缺少：Hibernate 方言配置、命名策略、批量写入配置、连接池配置 |
| **无自动配置注册** | 缺少 `META-INF/spring/AutoConfiguration.imports`，`JpaConfig` 不会被自动装配 |
| **缺少 BaseRepository** | 无自定义 `JpaRepository` 基类，不能提供通用的软删除、批量操作等增强方法 |
| **缺少 Specification 构建器** | 每个模块都手写 Specification，应提供 fluent builder 减少重复代码 |

### 3. eagle-resource-server-starter

| 缺失功能 | 说明 |
|----------|------|
| **公开端点不可配置** | `ResourceServerSecurityConfig` 中白名单路径硬编码（`/public/**`, `/actuator/**`, `/swagger-ui/**`），应通过 `@ConfigurationProperties` 外部化 |
| **缺少 Token 内省端点支持** | 只支持 JWT（本地验证），不支持 Opaque Token + 内省端点模式 |
| **CacheConfig 位置错误** | 缓存配置放在 resource-server-starter 里不合理，应独立或移到 redis-starter |

### 4. eagle-redis-starter

| 缺失功能 | 说明 |
|----------|------|
| **工具类未注册为 Bean** | `RedisLockUtil` 和 `RedisRateLimiter` 作为工具类依赖 `RedissonClient`/`StringRedisTemplate`，没有注册为 Bean，使用方需要手动 `new` |
| **缺少多级缓存** | CLAUDE.md 描述「Redisson + Caffeine 多级缓存」，但实际只有 Redis CacheManager，无 L1（Caffeine）+ L2（Redis）联动 |
| **缺少缓存穿透/击穿/雪崩防护** | 无 Null 值缓存、布隆过滤器、互斥锁等常见防护机制 |

### 5. eagle-feign-starter

| 缺失功能 | 说明 |
|----------|------|
| **缺少重试与熔断配置** | 无 Retry、CircuitBreaker（Resilience4j）集成，远程调用失败直接抛异常 |
| **缺少请求/响应日志** | `Logger.Level.BASIC` 只记录方法和 URL，建议提供可配置的 FULL 级别 |
| **FeignErrorDecoder 异常映射不完整** | 409 映射为 `DomainException` 不准确，应为 `ConflictException` |

### 6. eagle-gateway-server

| 缺失功能 | 说明 |
|----------|------|
| **Sentinel 限流规则为空** | 只配了 `BlockRequestHandler`，没有定义任何限流规则（QPS/并发数/热点参数），Sentinel 形同虚设 |
| **无熔断降级** | 无 fallback URI 配置，后端服务不可用时直接 502 |
| **缺少请求体大小限制** | 无 `RequestSize` 过滤器，大文件上传可能打爆网关 |
| **安全头缺失** | 无 `AddResponseHeader`（HSTS、X-Content-Type-Options、X-Frame-Options 等安全响应头） |
| **Redis 未使用** | `build.gradle` 引了 `spring-boot-starter-data-redis-reactive`，但没有任何地方用到（Redis 限流、缓存路由等） |

### 7. eagle-system-server

| 缺失功能 | 说明 |
|----------|------|
| **DDD 分层未完全遵循规范** | Controller 直接注入 ApplicationService 实现类，未经过 Driving Port 接口（`application/port/`），与 `.claude/rules/02-architecture.md` 的六边形严格要求不符 |
| **缺少菜单/权限资源管理** | 有 Role、DataScope，但无 `Menu`（菜单）、`Permission`（权限点）聚合根，RBAC 不完整 |
| **缺少在线用户管理实现** | `OnlineUserPort` 接口已定义，但只有 `NoOpOnlineUserAdapter`（空实现），`OnlineUserAdapter` 的 Redis 实现被注释/残缺 |
| **缺少 Spring Modulith 架构测试** | 规范反复强调的 `ModulithArchitectureTest` 不存在 |
| **缺少单元测试** | 整个 system-server 只有一个 contextLoads 空测试，0 业务测试覆盖 |
| **RSA 密钥每次重启生成** | `SecurityConfig` 中 `KeyPairGenerator` 每次启动生成新密钥对，重启后旧 JWT 全部失效，生产环境不可用 |
| **CORS 全开** | `allowedOriginPatterns("*")` + `allowCredentials(true)` 只适合开发环境，缺少 profile 区分 |
| **缺少 Flyway 迁移脚本** | DDL 依赖 Hibernate 自动生成，无版本化管理 |

## 三、已有组件需要改进

### 1. 架构层面

| 问题 | 位置 | 建议 |
|------|------|------|
| **Starter 自动配置缺失** | `eagle-common-starter`、`eagle-data-jpa-starter` | 补充 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`，否则 Bean 不会自动注册 |
| **eagle-common-starter 耦合 WebMVC** | `build.gradle` 依赖 `spring-boot-starter-web` | Gateway 是 WebFlux 技术栈，引入 common-starter 会导致 WebMVC/WebFlux 冲突。应将 Web 相关（`GlobalExceptionHandler`、`I18nConfig`）拆到独立的 `eagle-web-starter` |
| **工具类散落在 redis-starter** | `RedisLockUtil`、`RedisRateLimiter` | 应注册为 Spring Bean，或抽取独立 starter（`eagle-lock-starter`、`eagle-ratelimit-starter`），当前只是 POJO 工具类 |
| **CacheConfig 位置不合理** | `eagle-resource-server-starter` 内 | 缓存配置不属于资源服务器职责，应移到 `eagle-redis-starter` 或独立模块 |

### 2. 安全层面

| 问题 | 位置 | 建议 |
|------|------|------|
| **JWT 密钥不持久化** | `SecurityConfig.java` | 每次启动生成新 RSA 密钥对 → 重启后所有 Token 失效。应从 JKS/PKCS12 密钥库加载，或通过配置注入 |
| **刷新令牌 TTL 过长** | `application.yml` refresh-token: 2592000s | 30 天 refresh token 风险较高，建议配合 Token 轮转（rotation）和绝对过期策略 |
| **LoginRateLimitFilter 无持久化** | `LoginAttemptService` | 如果登录限流数据存在内存中，重启后清零，应存 Redis |
| **FeignAuthInterceptor 透传 Token** | `FeignAuthInterceptor.java` | 直接从 `RequestContextHolder` 取 Token 转发，在异步线程（`@Async`）中会丢失上下文 |

### 3. 代码质量

| 问题 | 位置 | 建议 |
|------|------|------|
| **RoleDept 不应是聚合根** | `base/domain/model/RoleDept.java` | 角色-部门关联是 Role 聚合的内部关系，应作为值对象或 `@ElementCollection`，不应有独立 Repository |
| **SysLog 不应是聚合根** | `base/domain/model/SysLog.java` | 日志是追加写入的只读记录，不需要 `@Version` 乐观锁和审计字段，继承 `BaseAggregateRoot` 浪费空间 |
| **FeignErrorDecoder 409 映射错误** | `FeignErrorDecoder.java` | HTTP 409 应映射为 `ConflictException`，当前映射为 `DomainException` |
| **SeataXidFilter 反射调用** | `SeataXidRequestInterceptor.java` | 用反射调 `RootContext.getXID()` 避免硬依赖，但 Seata 已是 compileOnly 依赖，可以用 `@ConditionalOnClass` + 直接调用更安全 |
| **EagleUser.attributes 可变** | `EagleUser.java` | `getAttributes()` 返回可变 Map，应返回 `Collections.unmodifiableMap()` |
| **BaseDomainEvent 冗余** | `eagle-common-starter` | 与 `BaseEvent` 功能重叠但缺少 `eventId`，应合并删除 |
| **测试覆盖率为 0** | 全项目 | 所有模块只有 `contextLoads()` 空测试，无业务逻辑测试 |

### 4. 配置与运维

| 问题 | 位置 | 建议 |
|------|------|------|
| **H2 文件数据库提交到 Git** | `db/eagle.mv.db` | 应加入 `.gitignore`，开发环境用内存模式或配置 `~/.eagle/` 路径 |
| **敏感配置明文** | `application.yml` | `admin.password`、WeChat `app-secret`、SMS `access-key-secret` 虽用了环境变量但有默认值，应移除默认值 |
| **application.yml profile 隔离不足** | `application-local.yml` / `application-dev.yml` | CORS、ddl-auto、Sentinel 等安全相关配置应严格按 profile 区分，当前 base `application.yml` 中的 CORS 全开 |
| **Gradle 构建缺少质量门禁** | `build.gradle` | 无 Checkstyle/PMD/SpotBugs 静态分析插件，无 JaCoCo 覆盖率要求 |

### P0 — 阻塞生产部署

以下问题任意一项未解决，服务重启或环境切换都会导致线上故障。

#### P0-1. JWT 密钥每次重启重新生成，旧 Token 全部失效

**问题定位：** `SecurityConfig.java:224-236`

```java
// 当前代码 — 每次启动生成全新 RSA 密钥对
@Bean
public JWKSource<SecurityContext> jwkSource() throws NoSuchAlgorithmException {
    KeyPairGenerator keyPairGenerator = KeyPairGenerator.getInstance("RSA");
    keyPairGenerator.initialize(2048);
    KeyPair keyPair = keyPairGenerator.generateKeyPair();
    // ...
}
```

**影响：**
- 服务重启后所有已签发的 Access Token 和 Refresh Token 立即失效
- 多实例部署时不同实例签发的 Token 互不认可
- Gateway 的 `jwk-set-uri` 指向单一实例，扩容后 JWT 验证随机失败

**修复方案：**

1. 生成 PKCS12 密钥库文件：
```bash
keytool -genkeypair -alias eagle-jwt -keyalg RSA -keysize 2048 \
  -storetype PKCS12 -keystore jwt-keystore.p12 \
  -storepass ${EAGLE_JWT_KEYSTORE_PASSWORD} -validity 3650
```

2. 新增 `JwtKeyProperties`（`infrastructure/config/`）：
```java
@ConfigurationProperties(prefix = "eagle.jwt")
public class JwtKeyProperties {
    /** 密钥库路径，如 classpath:jwt-keystore.p12 或 file:/etc/eagle/jwt-keystore.p12 */
    private Resource keystoreLocation;
    /** 密钥库密码 */
    private String keystorePassword;
    /** 密钥别名 */
    private String keyAlias = "eagle-jwt";
}
```

3. 改写 `jwkSource()` 从密钥库加载：
```java
@Bean
public JWKSource<SecurityContext> jwkSource(JwtKeyProperties props) throws Exception {
    KeyStore ks = KeyStore.getInstance("PKCS12");
    try (InputStream is = props.getKeystoreLocation().getInputStream()) {
        ks.load(is, props.getKeystorePassword().toCharArray());
    }
    RSAKey rsaKey = RSAKey.load(ks, props.getKeyAlias(),
            props.getKeystorePassword().toCharArray());
    return new ImmutableJWKSet<>(new JWKSet(rsaKey));
}
```

4. `application.yml` 配置：
```yaml
eagle:
  jwt:
    keystore-location: classpath:jwt-keystore.p12  # 开发环境
    # keystore-location: file:/etc/eagle/jwt-keystore.p12  # 生产环境
    keystore-password: ${EAGLE_JWT_KEYSTORE_PASSWORD}
    key-alias: eagle-jwt
```

#### P0-2. OAuth2 授权数据使用内存存储，重启丢失所有活跃令牌

**问题定位：** `SecurityConfig.java:92-94`

```java
// 当前代码 — 内存存储，重启即清空
@Bean
public OAuth2AuthorizationService authorizationService() {
    return new InMemoryOAuth2AuthorizationService();
}
```

**影响：**
- 服务重启后所有已授权的 OAuth2 Authorization（包括 authorization_code、refresh_token）全部丢失
- 用户必须重新走授权流程
- 多实例部署时授权码在 A 实例生成，在 B 实例兑换时找不到

**修复方案：**

替换为 JDBC 持久化实现（Spring Authorization Server 原生支持）：

1. `build.gradle` 添加依赖：
```groovy
implementation 'org.springframework.boot:spring-boot-starter-jdbc'
```

2. 替换 Bean：
```java
@Bean
public OAuth2AuthorizationService authorizationService(JdbcOperations jdbcOperations,
        RegisteredClientRepository registeredClientRepository) {
    return new JdbcOAuth2AuthorizationService(jdbcOperations, registeredClientRepository);
}

@Bean
public OAuth2AuthorizationConsentService authorizationConsentService(JdbcOperations jdbcOperations,
        RegisteredClientRepository registeredClientRepository) {
    return new JdbcOAuth2AuthorizationConsentService(jdbcOperations, registeredClientRepository);
}
```

3. 数据库建表（Spring Authorization Server 提供的标准 DDL）：
```sql
-- oauth2_authorization 表：存储授权记录
-- oauth2_authorization_consent 表：存储用户授权同意
-- 脚本位于 spring-security-oauth2-authorization-server JAR 内
-- org/springframework/security/oauth2/server/authorization/
--   oauth2-authorization-schema.sql
--   oauth2-authorization-consent-schema.sql
```

#### P0-3. Starter 自动配置注册缺失，Bean 不会被自动装配

**问题定位：**
- `eagle-common-starter` — 无 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`
- `eagle-data-jpa-starter` — 同上

**影响：**
- `GlobalExceptionHandler`、`AsyncConfig`、`I18nConfig`、`MessageSourceUtil` 等核心 Bean 不会被自动注册
- 当前之所以能工作，是因为 `eagle-system-server` 的 `@SpringBootApplication` 包扫描路径 `com.eagle.system` 恰好不会扫到 `com.eagle.common`
- 如果新建其他微服务（非 system-server），这些 Bean **确定不会生效**
- `JpaConfig`（AuditorAware）同理，审计字段 `createBy`/`updateBy` 在新服务中将为 null

**修复方案：**

1. 创建 `eagle-common-starter` 自动配置文件：

文件路径：`eagle-starter/eagle-common-starter/src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`

```
com.eagle.common.config.AsyncConfig
com.eagle.common.config.I18nConfig
com.eagle.common.handler.GlobalExceptionHandler
com.eagle.common.i18n.MessageSourceUtil
```

注意：`I18nConfig` 实现了 `WebMvcConfigurer`，会与 WebFlux（Gateway）冲突。建议：
- 给 `I18nConfig` 加条件注解 `@ConditionalOnWebApplication(type = SERVLET)`
- 给 `GlobalExceptionHandler` 加条件注解 `@ConditionalOnWebApplication(type = SERVLET)`
- 或者将 Web 相关组件拆到独立的 `eagle-web-starter`（P1 处理）

2. 创建 `eagle-data-jpa-starter` 自动配置文件：

文件路径：`eagle-starter/eagle-data-jpa-starter/src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`

```
com.eagle.datajpa.config.JpaConfig
```

同时 `JpaConfig` 应改为 `@AutoConfiguration`：
```java
@AutoConfiguration
@EnableJpaAuditing
@ConditionalOnClass(name = "jakarta.persistence.EntityManager")
public class JpaConfig {
    // ...
}
```

#### P0-4. 数据库迁移工具缺失，DDL 依赖 Hibernate 自动生成

**问题定位：**
- `application-local.yml` 使用 `ddl-auto: update`（H2）
- `application-dev.yml` 使用 `ddl-auto: update`（MySQL）
- 无 Flyway/Liquibase 依赖和迁移脚本

**影响：**
- 生产环境使用 `ddl-auto: update` 风险极高：Hibernate 可能执行意外的 ALTER TABLE（加列、改类型），但**不会删列**，导致表结构与实体不一致
- 无法回滚 DDL 变更
- 多人协作时表结构变更无版本控制，容易冲突
- 违反 `.claude/rules/10-database.md` 明确要求

**修复方案：**

1. 根 `build.gradle` 添加 Flyway 版本管理：
```groovy
ext {
    set('flywayVersion', '11.8.0')
}
```

2. `eagle-data-jpa-starter` 的 `build.gradle` 添加：
```groovy
api 'org.flywaydb:flyway-core'
api 'org.flywaydb:flyway-mysql'  // MySQL 方言支持
```

3. 生成 baseline 迁移脚本（基于当前 Hibernate 自动生成的表结构）：
```bash
# 启动应用让 Hibernate 生成完整 DDL，然后导出
mysqldump -u root -p eagle_db --no-data > V1__baseline.sql
```

4. 迁移脚本放置位置：
```
eagle-base-server/eagle-system-server/src/main/resources/
└── db/migration/
    └── V1__baseline.sql
```

5. 配置调整：
```yaml
# application.yml (base)
spring:
  jpa:
    hibernate:
      ddl-auto: validate  # 只校验不修改

# application-local.yml (开发环境可选)
spring:
  flyway:
    enabled: true
    baseline-on-migrate: true  # 首次运行时自动 baseline
```

#### P0-5. 敏感配置有硬编码默认值

**问题定位：** `application.yml:29`

```yaml
eagle:
  admin:
    password: ${EAGLE_ADMIN_PASSWORD:123456}  # 默认密码 123456
```

**影响：**
- 如果部署时忘记设置 `EAGLE_ADMIN_PASSWORD` 环境变量，管理员账户使用弱密码 `123456` 运行
- 安全审计红线问题

**修复方案：**

1. 移除默认值，启动时强制校验：
```yaml
eagle:
  admin:
    password: ${EAGLE_ADMIN_PASSWORD}  # 无默认值，未设置时启动报错
```

2. 在 `AdminProperties` 中添加 JSR-303 校验：
```java
@ConfigurationProperties(prefix = "eagle.admin")
@Validated
public class AdminProperties {
    @NotBlank(message = "管理员密码不能为空，请设置环境变量 EAGLE_ADMIN_PASSWORD")
    @Size(min = 8, message = "管理员密码长度不能少于 8 位")
    private String password;
```

#### P1-2. Feign 远程调用缺少容错与异常映射错误

**问题定位：**
- `FeignErrorDecoder.java` — 409 映射为 `DomainException` 而非 `ConflictException`
- `FeignAuthInterceptor.java` — 从 `RequestContextHolder` 取 Token，在 `@Async` 线程中会丢失

**影响：**

- 异步调用远程服务时 Token 丢失 → 401 鉴权失败
- 远程服务短暂不可用时无重试，直接失败；持续不可用时无熔断，线程池被打满

**修复方案：**

1. 修复 `FeignErrorDecoder` 异常映射（`FeignErrorDecoder.java`）：

```java
// 修正前
case 409, 400 -> new DomainException(errorCode);

// 修正后
case 400 -> errorCode.toDomainException();
case 409 -> errorCode.toConflictException();
```

2. 修复异步线程 Token 丢失（`FeignAuthInterceptor.java`）：

```java
/**
 * 当前实现依赖 RequestContextHolder，在 @Async 线程中为 null。
 * 改为：在主线程创建 Feign 客户端时，将 Token 绑定到 InheritableThreadLocal，
 * 或使用 TaskDecorator 在提交异步任务时传播 RequestAttributes。
 */

// 方案 A：AsyncConfig 中添加 TaskDecorator
@Bean(name = "taskExecutor")
@Override
public Executor getAsyncExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    // ... 现有配置 ...
    executor.setTaskDecorator(runnable -> {
        RequestAttributes attrs = RequestContextHolder.getRequestAttributes();
        return () -> {
            try {
                if (attrs != null) {
                    RequestContextHolder.setRequestAttributes(attrs, true);
                }
                runnable.run();
            } finally {
                RequestContextHolder.resetRequestAttributes();
            }
        };
    });
    return executor;
}
```

#### P1-3. 补充注解驱动组件（限流、幂等、分布式锁）

**问题定位：**
- `RedisLockUtil.java` — 纯工具类，需手写 `try/finally` 获取释放锁，易遗漏
- `RedisRateLimiter.java` — 纯工具类，每个 Controller 方法需手动调用
- 幂等控制 — 完全缺失

**影响：**
- 开发者忘记 `finally { unlock() }` 导致死锁
- 限流逻辑散落在业务代码中，不统一
- 无幂等保护，重复提交导致重复创建订单等

**修复方案：**

**方案 A：新建 `eagle-idempotent-starter`（推荐单独模块）**

```java
// 1. 注解定义
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Idempotent {
    /** 幂等 key 的 SpEL 表达式，如 "#request.orderNo" */
    String key();
    /** 幂等窗口时间（秒） */
    int expireSeconds() default 10;
    /** 重复请求的提示消息 i18n key */
    String message() default "error.common.duplicate_request";
}

// 2. AOP 切面
@Aspect
@RequiredArgsConstructor
public class IdempotentAspect {
    private final StringRedisTemplate redisTemplate;

    @Around("@annotation(idempotent)")
    public Object around(ProceedingJoinPoint pjp, Idempotent idempotent) throws Throwable {
        String key = "idempotent:" + parseSpEL(idempotent.key(), pjp);
        Boolean acquired = redisTemplate.opsForValue()
                .setIfAbsent(key, "1", Duration.ofSeconds(idempotent.expireSeconds()));
        if (Boolean.FALSE.equals(acquired)) {
            throw CommonErrorCode.DUPLICATE_REQUEST.toDomainException();
        }
        try {
            return pjp.proceed();
        } catch (Throwable t) {
            // 业务异常时删除幂等 key，允许重试
            redisTemplate.delete(key);
            throw t;
        }
    }
}

// 3. 使用示例
@PostMapping
@Idempotent(key = "#request.orderNo", expireSeconds = 30)
public OrderResponse createOrder(@Valid @RequestBody CreateOrderRequest request) { }
```

**方案 B：增强 `eagle-redis-starter` 中的锁和限流**

```java
// 1. @DistributedLock 注解
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface DistributedLock {
    /** 锁 key 的 SpEL 表达式 */
    String key();
    /** 等待锁的超时时间（秒） */
    int waitTime() default 3;
    /** 持有锁的最长时间（秒） */
    int leaseTime() default 30;
}

// 2. AOP 切面 — 封装 RedisLockUtil 的 try/finally
@Aspect
@RequiredArgsConstructor
public class DistributedLockAspect {
    private final RedisLockUtil redisLockUtil;

    @Around("@annotation(lock)")
    public Object around(ProceedingJoinPoint pjp, DistributedLock lock) throws Throwable {
        String key = parseSpEL(lock.key(), pjp);
        RLock rLock = redisLockUtil.getLock(key);
        boolean acquired = rLock.tryLock(lock.waitTime(), lock.leaseTime(), TimeUnit.SECONDS);
        if (!acquired) {
            throw CommonErrorCode.LOCK_ACQUIRE_FAILED.toDomainException();
        }
        try {
            return pjp.proceed();
        } finally {
            if (rLock.isHeldByCurrentThread()) {
                rLock.unlock();
            }
        }
    }
}

// 3. @RateLimit 注解
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface RateLimit {
    /** 限流 key 前缀（默认取方法全限定名） */
    String key() default "";
    /** 每秒允许的请求数 */
    int qps() default 10;
    /** 令牌桶容量 */
    int capacity() default 20;
}

// 4. AOP 切面 — 封装 RedisRateLimiter
@Aspect
@RequiredArgsConstructor
public class RateLimitAspect {
    private final RedisRateLimiter rateLimiter;

    @Around("@annotation(limit)")
    public Object around(ProceedingJoinPoint pjp, RateLimit limit) throws Throwable {
        String key = limit.key().isEmpty()
                ? pjp.getSignature().toShortString()
                : limit.key();
        if (!rateLimiter.isAllowed(key, limit.capacity(), limit.qps())) {
            throw CommonErrorCode.RATE_LIMITED.toDomainException();
        }
        return pjp.proceed();
    }
}

// 5. 使用示例
@PostMapping("/{id}/lock")
@DistributedLock(key = "'account:lock:' + #id")
@RateLimit(qps = 5, capacity = 10)
public void lockAccount(@PathVariable Long id) { }
```

**自动配置注册：**

```java
// eagle-redis-starter 的 AutoConfiguration 中追加

@ConditionalOnBean(RedisLockUtil.class)
public DistributedLockAspect distributedLockAspect(RedisLockUtil redisLockUtil) {
    return new DistributedLockAspect(redisLockUtil);
}

@Bean
@ConditionalOnBean(RedisRateLimiter.class)
public RateLimitAspect rateLimitAspect(RedisRateLimiter rateLimiter) {
    return new RateLimitAspect(rateLimiter);
}
```

- 潜在缺陷（空指针、资源泄漏）靠人工 Code Review 发现
- 测试覆盖率无底线

**修复方案：**

在根 `build.gradle` 的 `subprojects {}` 块中添加：

```groovy
subprojects {
    // ===== JaCoCo 覆盖率 =====
    apply plugin: 'jacoco'

    jacoco {
        toolVersion = '0.8.13'
    }

    tasks.named('test') {
        finalizedBy jacocoTestReport
    }

    jacocoTestReport {
        dependsOn test
        reports {
            xml.required = true   // CI 解析用
            html.required = true  // 人工查看用
        }
    }

    jacocoTestCoverageVerification {
        violationRules {
            rule {
                limit {
                    minimum = 0.60  // 起步 60%，逐步提高
                }
            }
        }
    }

    // 将覆盖率检查绑定到 check 任务
    tasks.named('check') {
        dependsOn jacocoTestCoverageVerification
    }

    // ===== Checkstyle 代码风格 =====
    apply plugin: 'checkstyle'

    checkstyle {
        toolVersion = '10.24.0'
        configFile = rootProject.file('config/checkstyle/google_checks.xml')
        maxWarnings = 0  // 警告也不放过
    }
}
```

配套文件：
- 下载 Google Java Style 的 Checkstyle 配置：`config/checkstyle/google_checks.xml`
- 将行宽调整为 100（与 `.claude/rules/08-code-style.md` 一致）

运行方式：
```bash
./gradlew check                    # 覆盖率 + 风格检查
./gradlew jacocoTestReport         # 仅生成覆盖率报告
./gradlew checkstyleMain           # 仅检查代码风格
```

**问题定位：**

**影响：**

```xml
<configuration>
    <include resource="org/springframework/boot/logging/logback/defaults.xml"/>

    <!-- 开发环境：彩色文本输出 -->
    <springProfile name="local">
        <include resource="org/springframework/boot/logging/logback/console-appender.xml"/>
        <root level="INFO">
            <appender-ref ref="CONSOLE"/>
        </root>
    </springProfile>

                </customFields>

        </appender>

        </root>
```

```groovy
implementation 'io.micrometer:micrometer-registry-prometheus'
```

```groovy
// 当前缺失，需要添加
```

#### P2-5. 代码建模问题修复

**问题 A：RoleDept 有独立 Repository 违反子实体规范**

**问题定位：** `RoleDept.java` 继承 `BaseEntity`，但有独立的 `RoleDeptRepository`。

按 `.claude/rules/02-architecture.md`：「只有聚合根才能拥有 Repository，子实体禁止创建独立 Repository」。RoleDept 是 Role 和 Dept 之间的关联关系，用于 CUSTOM 数据范围配置，不具备独立业务生命周期。

**修复方案：** 改为通过 Role 聚合根管理。

```java
// Role.java — 使用 @ElementCollection 替代独立实体
@ElementCollection(fetch = FetchType.LAZY)
@CollectionTable(name = "sys_role_dept",
        joinColumns = @JoinColumn(name = "role_id"))
@Column(name = "dept_id")
private Set<Long> customDeptIds = new HashSet<>();

/** 配置自定义数据范围的部门 */
public void assignCustomDepts(Set<Long> deptIds) {
    if (this.dataScope != DataScope.CUSTOM) {
        throw SystemErrorCode.DATA_SCOPE_NOT_CUSTOM.toDomainException();
    }
    this.customDeptIds = new HashSet<>(deptIds);
}
```

然后删除 `RoleDept.java` 和 `RoleDeptRepository.java`。

**问题 B：EagleUser.attributes 返回可变 Map**

**问题定位：** `EagleUser.java:30-31`

```java
// 当前 — 外部可直接修改内部状态
private final Map<String, Object> attributes = new HashMap<>();
// Lombok @Getter 直接暴露引用
```

**修复方案：**

```java
// 方案：覆盖 getter 返回不可变视图
public Map<String, Object> getAttributes() {
    return Collections.unmodifiableMap(attributes);
}

// 提供安全的写入方法
public void setAttribute(String key, Object value) {
    this.attributes.put(key, value);
}
```

**问题 C：BaseDomainEvent 与 BaseEvent 功能重复**

**问题定位：**
- `BaseEvent.java` — 有 `eventId`（UUID）+ `occurredOn` + `getEventType()`
- `BaseDomainEvent.java` — 只有 `occurredOn`，无 `eventId`

两个类都叫「领域事件基类」，语义重叠。

**修复方案：**

1. 确认所有事件子类的继承关系：

```bash
grep -r "extends BaseDomainEvent" --include="*.java"
grep -r "extends BaseEvent" --include="*.java"
```

2. 将 `BaseDomainEvent` 的使用方迁移到 `BaseEvent`
3. 删除 `BaseDomainEvent.java`
4. 如果有事件不需要 `eventId`，保留 `BaseDomainEvent` 但重命名为更明确的名称（如 `SimpleEvent`），避免与 `BaseEvent` 混淆

**问题 D：Result\<T\> 统一包装类与 API 规范冲突**

**问题定位：** `Result.java` 提供 `success(data)` / `error(message)` 包装，但 `.claude/rules/03-api.md` 明确要求：

> 直接返回数据，不使用统一包装类，通过 HTTP 状态码传递语义。

**修复方案：**

1. 确认 `Result<T>` 是否在任何 Controller 中使用：

```bash
grep -r "Result<" --include="*.java" eagle-base-server/
```

2. 如果未被使用 → 直接删除 `Result.java`
3. 如果被 Feign 远程调用等内部场景使用 → 保留但添加 `@Deprecated` 注解并在 Javadoc 中说明仅限内部通信，Controller 层禁止使用

#### P3-1. 操作日志抽取为独立 Starter

**现状：** `SysLog` 实体、`LogApplicationService`、`LogController`、`LogCleanupTask` 全部硬编码在 `eagle-system-server` 的 `base` 模块中。新增其他微服务时无法复用日志采集能力。

**目标：** 新建 `eagle-log-starter`，提供 `@OperationLog` 注解 + AOP 自动采集。

**方案概要：**

```
eagle-log-starter/
├── annotation/
│   └── OperationLog.java       # @OperationLog(module = "用户管理", type = "创建")
├── aspect/
│   └── OperationLogAspect.java # AOP 拦截，自动采集请求参数、响应结果、耗时、异常
├── event/
│   └── OperationLogEvent.java  # 异步事件，解耦日志写入
├── handler/
│   └── OperationLogHandler.java # @Async 事件处理，写入存储
├── storage/
│   ├── LogStorage.java          # SPI 接口
│   ├── JpaLogStorage.java       # JPA 实现（默认）
│   └── MqLogStorage.java        # MQ 实现（可选，发送到日志中心）
├── config/
│   └── LogAutoConfiguration.java
└── properties/
    └── LogProperties.java       # 保留天数、清理 cron、存储类型
```

```java
// 使用示例
@PostMapping
@OperationLog(module = "账户管理", type = "创建", description = "创建新账户")
public void createAccount(@Valid @RequestBody CreateAccountRequest request) { }
```

迁移步骤：
1. 新建 `eagle-log-starter` 模块
2. 将 `SysLog`、`LogRepository`、`LogCleanupTask` 迁入
3. `eagle-system-server` 引入该 starter，删除本地日志代码
4. `LogController` 保留在 system-server（查询接口属于系统管理域）

#### P3-2. 多级缓存实现（Caffeine L1 + Redis L2）

**现状：** `eagle-redis-starter` 的 `RedisCacheConfig` 只配置了 Redis CacheManager，CLAUDE.md 描述的「Redisson + Caffeine 多级缓存」未实现。

**方案概要：**

```java
/**
 * 多级缓存管理器
 * L1: Caffeine 本地缓存（毫秒级读取，容量有限）
 * L2: Redis 分布式缓存（跨节点共享）
 *
 * 读取路径：L1 hit → 返回 | L1 miss → L2 hit → 回填 L1 → 返回 | L2 miss → 数据库
 * 写入/失效：删除 L1 + L2，通过 Redis Pub/Sub 通知其他节点清除 L1
 */
public class MultiLevelCacheManager implements CacheManager {

    private final CaffeineCacheManager l1;
    private final RedisCacheManager l2;
    private final RedisMessageListenerContainer listenerContainer;

    @Override
    public Cache getCache(String name) {
        return new MultiLevelCache(
                l1.getCache(name),
                l2.getCache(name),
                listenerContainer);
    }
}
```

关键点：
- L1 Caffeine：最大 1000 条，TTL 5 分钟，LRU 淘汰
- L2 Redis：TTL 30 分钟
- 缓存失效通过 Redis Pub/Sub 广播，所有节点同步清除 L1
- Null 值缓存（防穿透）：缓存 `NullValue.INSTANCE`，TTL 1 分钟

#### P3-3. DDD 分层严格化（Driving Port 接口）

**现状：** Controller 直接注入 `ApplicationService` 实现类：

```java
// 当前 — Controller 与应用服务实现类耦合
@RequiredArgsConstructor
public class UserController {
    private final UserApplicationService userApplicationService;
}
```

**目标：** 按 `.claude/rules/02-architecture.md` 的六边形严格模式，引入 Driving Port。

**方案概要：**

```java
// 1. application/port/ — 入站端口接口（按用例分组）
public interface UserCommandPort {
    void updateUser(Long id, UpdateUserRequest request);
    void assignRoles(Long userId, Set<Long> roleIds);
    void assignDept(Long userId, Long deptId);
}

public interface UserQueryPort {
    UserResponse getUserById(Long id);
    Page<UserSummary> queryUsers(Pageable pageable);
}

// 2. application/service/ — 实现端口
@Service
@Transactional
public class UserApplicationService implements UserCommandPort, UserQueryPort {
    // 现有逻辑不变
}

// 3. web/controller/ — 只依赖端口接口
@RestController
@RequiredArgsConstructor
public class UserController {
    private final UserCommandPort userCommandPort;
    private final UserQueryPort userQueryPort;
}
```

好处：
- Controller 与实现类解耦，新增 gRPC/MQ 入口时复用同一 Port
- 测试 Controller 时只需 mock Port 接口，不需要知道实现细节
- 为未来 CQRS 读写分离做准备（Command 和 Query 可拆为不同实现）

评估：工作量较大（每个模块需新增 Port 接口），建议在新模块中直接采用，老模块逐步迁移。

#### P3-4. 代码生成器（DDD 全套脚手架）

**现状：** 每次新增聚合根需手写 10+ 个文件：entity → repository → domain service → application service → controller → request DTO → response DTO → mapper → event → error code。

生成的文件：

```
base/
```

#### P3-5. eagle-tracing-starter 增强（日志 traceId 注入 + 跨线程传播）

**现状：** `eagle-tracing-starter` 仅配置了 Zipkin reporter，缺少：
- MDC 中自动注入 traceId/spanId（日志中看不到链路信息）
- `@Async` 线程池的 traceId 传播（异步任务断链）
- Feign 调用的 traceId 传播（已在 `FeignAuthInterceptor` 中硬编码 B3 头，应由 tracing-starter 统一管理）

**方案概要：**

```java
// 1. MDC 自动注入（TracingAutoConfiguration 中追加）
@Bean
@ConditionalOnBean(Tracer.class)
public MdcContextLifecycleHandler mdcHandler() {
    // Micrometer Tracing 自动将 traceId/spanId 写入 MDC
    // logback pattern 中使用 %X{traceId} 即可
    return new MdcContextLifecycleHandler();
}

// 2. 异步线程 traceId 传播 — 装饰 AsyncConfig 的 TaskExecutor
@Bean
public TaskDecorator tracingTaskDecorator(Tracer tracer) {
    return runnable -> {
        Span currentSpan = tracer.currentSpan();
        return () -> {
            try (Tracer.SpanInScope ws = tracer.withSpan(currentSpan)) {
                runnable.run();
            }
        };
    };
}

// 3. 移除 FeignAuthInterceptor 中的硬编码 B3 头
// 改为依赖 Micrometer Tracing 的 ObservationFeignRequestInterceptor 自动注入
```
