Eagle Cloud 项目改进计划

背景

Eagle Cloud 是一个基于 DDD 原则构建的 Spring Boot 微服务平台。通过全面分析项目代码、配置和架构，发现了多个需要改进的方面，涉及安全性、测试覆盖、文档完善、代码质量和配置管理等。

发现的主要问题

1. 安全问题（高优先级）

1.1 硬编码的客户端密钥

文件: eagle-base-server/eagle-system-server/src/main/resources/application.yml:13
client-secret: "{noop}123456"
问题: OAuth2 客户端密钥使用明文 "123456"，存在严重安全风险
影响: 生产环境中任何人都可以使用此密钥进行认证

1.2 CORS 配置过于宽松

文件: eagle-base-server/eagle-system-server/src/main/java/com/eagle/system/config/SecurityConfig.java:134
config.setAllowedOrigins(List.of("*"));
问题: 允许所有来源的跨域请求，注释说明"生产改为部分跨域"但未实现
影响: 可能导致 CSRF 攻击

1.3 CSRF 保护被禁用

文件: SecurityConfig.java:70,98
.csrf(AbstractHttpConfigurer::disable)
问题: 完全禁用 CSRF 保护，虽然注释说明"JWT 无状态"，但仍有表单登录
影响: 表单登录端点可能受到 CSRF 攻击

1.4 JWT 密钥每次启动重新生成

文件: SecurityConfig.java:144-156
KeyPairGenerator keyPairGenerator = KeyPairGenerator.getInstance("RSA");
keyPairGenerator.initialize(2048);
KeyPair keyPair = keyPairGenerator.generateKeyPair();
问题: RSA 密钥对在每次应用启动时重新生成，导致之前签发的 JWT 失效
影响: 应用重启后所有用户需要重新登录

1.5 本地配置文件使用硬编码路径

文件: application-local.yml:4
url: jdbc:h2:file:D:/matchmaking-sites/eagle
问题: 使用 Windows 绝对路径，不具备跨平台性

2. 测试覆盖不足（高优先级）

2.1 测试文件质量低

所有测试文件都只包含空的 contextLoads() 测试：
- EagleSystemApplicationTests.java
- EagleGatwayApplicationTests.java
- EagleCommonApplicationTests.java
- 等等

问题: 没有实际的单元测试或集成测试

2.2 缺失的测试类型

- 领域模型测试: User 聚合根有复杂的业务逻辑（密码修改、角色分配、锁定/解锁），但没有测试
- 领域事件测试: UserCreatedEvent、UserPasswordChangedEvent 等事件没有测试
- 仓储层测试: UserRepository 等仓储接口没有测试
- 应用服务测试: UserService、RegisterApplicationService 等没有测试
- 安全配置测试: SecurityConfig 的复杂配置没有测试

3. 文档缺失（中优先级）

3.1 缺少项目 README

问题: 根目录没有 README.md 文件，只有 HELP.md（Spring 生成的通用文档）
影响: 新开发者无法快速了解项目

3.2 部署文档为空

文件: eagle-doc/部署文档.md
问题: 文件大小为 0 字节，完全为空

3.3 API 文档配置不完整

虽然引入了 SpringDoc OpenAPI，但没有看到相关的配置类或注解使用

4. 代码质量问题（中优先级）

4.1 BaseEntity 和 BaseAggregateRoot 职责重复

文件:
- eagle-common-starter/src/main/java/com/eagle/common/base/BaseEntity.java
- eagle-common-starter/src/main/java/com/eagle/common/base/BaseAggregateRoot.java

问题: 两个类都有相同的审计字段（id, createBy, updateBy, createTime, updateTime, version），BaseAggregateRoot 继承 AbstractAggregateRoot 但也重复定义了这些字段

4.2 Post 实体继承错误的基类

文件: eagle-base-server/eagle-system-server/src/main/java/com/eagle/system/base/domain/model/Post.java:24
public class Post extends BaseEntity
问题: Post 作为领域实体应该继承 BaseAggregateRoot（如果是聚合根）或不继承（如果是实体），而不是 BaseEntity

4.3 User 实体的 Setter 方法破坏封装

文件: User.java:286-324
问题: 虽然注释说明"仅供 JPA 和 MapStruct 使用"，但 public setter 仍然可以被业务代码调用，破坏了充血模型的封装性

4.4 UserRepository 使用 @RepositoryRestResource

文件: UserRepository.java:20
@RepositoryRestResource(collectionResourceRel = "users", path = "user")
问题: 自动暴露 REST 端点可能绕过业务逻辑和安全检查

5. 配置管理问题（中优先级）

5.1 缺少环境配置文件

只有 application.yml 和 application-local.yml，缺少：
- application-dev.yml
- application-test.yml
- application-prod.yml

5.2 缺少 Docker Compose 配置

虽然 HELP.md 提到了 compose.yaml，但实际只有 eagle-base-server/docker-compose.yml，且未检查其内容

5.3 缺少日志配置

没有看到 logback-spring.xml 或日志相关配置

6. 依赖和构建问题（低优先级）

6.1 依赖范围问题

文件: build.gradle:150
implementation 'org.springframework.boot:spring-boot-starter-test'
问题: 测试依赖应该使用 testImplementation 而不是 implementation

6.2 Lombok 和 MapStruct 配置

虽然配置了 lombok-mapstruct-binding，但需要确保注解处理器顺序正确

7. 架构和设计问题（低优先级）

7.1 领域事件未使用 Spring Data 的机制

文件: BaseAggregateRoot.java:44
private final List<BaseEvent> domainEvents = new ArrayList<>();
问题: 自定义了 domainEvents 列表，但 BaseAggregateRoot 已经继承了 AbstractAggregateRoot，后者已经提供了事件管理

7.2 缺少全局异常处理

没有看到 @ControllerAdvice 或全局异常处理器

7.3 缺少统一响应格式

没有看到统一的 API 响应���装类（如 Result、Response）

改进优先级

高优先级（必须修复）

1. 修复安全问题（硬编码密钥、CORS、JWT 密钥管理）
2. 添加核心业务逻辑的单元测试
3. 创建项目 README.md

中优先级（建议修复）

4. 完善环境配置文件
5. 修复 BaseEntity/BaseAggregateRoot 重复问题
6. 添加全局异常处理
7. 完善 API 文档配置
8. 移除 @RepositoryRestResource 或限制其访问

低优先级（可选优化）

9. 修复测试依赖范围
10. 添加日志配置
11. 完善部署文档
12. 添加统一响应格式

验证方法

安全性验证

1. 使用环境变量配置敏感信息
2. 运行应用并检查 CORS 配置是否生效
3. 测试 JWT 在应用重启后是否仍然有效

测试验证

1. 运行 ./gradlew test 确保所有测试通过
2. 检查测试覆盖率报告

文档验证

1. 新开发者能够通过 README.md 快速启动项目
2. API 文档可以通过 /swagger-ui.html 访问

建议的实施顺序

1. 第一阶段：安全修复（1-2 天）
- 将敏感配置移到环境变量
- 修复 CORS 配置
- 实现 JWT 密钥持久化
2. 第二阶段：测试补充（3-5 天）
- 为 User 聚合根添加单元测试
- 为核心应用服务添加集成测试
- 为仓储层添加测试
3. 第三阶段：文档完善（1-2 天）
- 创建 README.md
- 完善 API 文档配置
- 补充部署文档
4. 第四阶段：代码重构（2-3 天）
- 重构 BaseEntity/BaseAggregateRoot
- 添加全局异常处理
- 添加统一响应格式
5. 第五阶段：配置优化（1 天）
- 添加环境配置文件
- 添加日志配置
- 优化构建配置
